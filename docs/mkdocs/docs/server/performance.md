## Methodology

Each point was measured with `/emote stress-test 30s N N`. `N-player equivalent` in the chart does not represent an actual player count. It means that both of the following load parameters were set to `N`.

| Value             | Meaning in the implementation                                                                                                                                                                                                                                                    |
|-------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Instances `N`     | Creates `N` independent server-side emote playback instances and places their display entities in the world. Emotes are shuffled with a fixed seed and start at different playback positions. No additional `ServerPlayer` objects or player connections are created.            |
| Packet fanout `N` | Passes each changed display metadata packet through `N` in-memory Minecraft packet encoders. This includes packet codec, compression, length framing, and generated byte-count costs, but excludes socket transmission, network latency, and client-side decoding and rendering. |

Therefore, `75-player equivalent` is a **synthetic load approximating 75 simultaneous emotes with every changed packet delivered to 75 recipients**. It models a case where all players are within the same tracking range and can see every emote, but it is not a test performed with 75 connected players. Actual fanout and load can be lower when players are spread apart or only some of them use emotes.

## Interpretation

- To approximate a server setup commonly used in practice, the tests included FerriteCore, Krypton, and Lithium.
- Average MSPT remained stable at about 22 ms or lower through the 50-player equivalent load. At 75-player equivalent, it reached about 42 ms. This remained below the 50 ms tick budget, but the 47.50 ms p95 and 59.68 ms maximum indicate little remaining headroom and occasional overruns. At 100-player equivalent, the 68.12 ms average and 75.35 ms p95 consistently exceeded the tick budget.
- At 20 TPS, 600 ticks take 30 seconds. Total elapsed time remained around 30 seconds from the 10- through 75-player equivalent loads, but increased to 43.2 seconds at 100-player equivalent, where observed TPS fell to 14.66.
- As load increased, `Server/idle` decreased while `Network` rose from 0.4 to 35.7 seconds. At 100-player equivalent, network processing accounted for 82.6% of the total elapsed time, so network-related work represented most of the cost under high load rather than emote timeline evaluation.
- These results cannot be interpreted directly as the server's maximum player count. The actual limit depends on the proportion of players using emotes concurrently, player tracking ranges, displays per emote, server CPU, compression settings, other mods, and world load.
- The test system used 24 GB of memory in a single-channel configuration, so memory bandwidth may have affected the high-load results. Without a comparison against a dual-channel configuration, the size of that effect cannot be determined and memory bandwidth cannot be identified as the primary bottleneck.
